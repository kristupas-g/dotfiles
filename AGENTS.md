# AGENTS.md

macOS dotfiles for one person, linked into `$HOME` with GNU Stow (`stow .` from the repo root). `README.md` has the install steps.

## How the linking works

- `~/.config` is a single symlink to `~/dotfiles/.config` (stow folded the whole directory). Anything an app writes to `~/.config` lands in this repo. New apps show up as untracked directories; either track their config or add them to `.gitignore`. Never commit runtime state, logs, sockets, caches or credentials.
- Top-level dotfiles (`.tmux.conf`, `.gitignore`, `.alacritty.toml`, `.emacs.d`) and `bin/` are symlinked individually into `~`.
- `.stow-local-ignore` lists what stow must not link (README, `nix/`, `AGENTS.md`, `CLAUDE.md`, `.zshrc`, the convenience symlinks at the root). Because the file exists, stow's default ignore list is off: any new repo-only file at the root must be added there, or `stow .` will link it into `~`.
- The root symlinks `aerospace`, `k9s`, `karabiner`, `lazygit`, `nvim`, `wezterm` point into `.config/` for convenience. Edit through either path; it's the same file.
- Edits in the repo are live immediately because `~` points here. No re-stow is needed unless you add a new top-level file or directory.

## Neovim

- Everything is in one `init.lua`: options, keymaps, then a single `require('lazy').setup({...})` with every plugin spec inline. Add a plugin by adding a spec to that table; don't split it into `lua/plugins/` unless asked.
- The top of `init.lua` refuses to start on Neovim older than 0.12. Use the 0.12 APIs already in use there (`vim.lsp.config`, `vim.lsp.enable`, `vim.diagnostic.jump`).
- The leader is space. LSP keymaps are set in the `LspAttach` autocmd. Servers and tools are installed through mason-lspconfig and mason-tool-installer, and are configured with `vim.lsp.config(...)`. `ruby_lsp` runs through `mise x --`.
- `vim.g.vscode` is set when running inside VS Code (vscode-neovim). Then only `lua/vscode_workflow.lua` loads, and UI plugins stay off. Keep new UI plugins and options behind `if not in_vscode`.
- `gwt` is a local plugin loaded from `~/vinted/worktree-cli`. It is not in the repo.
- Plugin versions are pinned in `lazy-lock.json`. To update them, run `nvim --headless "+Lazy! sync" +qa` and commit the lockfile on its own.
- Smoke test after editing: `nvim --headless +qa` must exit without output.

## herdr and the Herdr app

- `.config/herdr/config.toml` is the terminal multiplexer. Its keys mirror `.tmux.conf` (prefix `ctrl+a`, `h/j/k/l` focus, `r`/`d` splits, `q` close, `%` reload); keep the two in sync when changing bindings. `.gitignore` ignores everything in `.config/herdr/` except `config.toml`.
- `.config/herdr-app/` is the GUI app. Only `settings.json`, `keys.json`, `programs.json` and `layouts/main-copy.json` are user-owned and tracked; the rest is ignored. `.config/herdr-app/AGENTS.md` is the app's own reference: it's rewritten on every start, so read it there before editing. Shipped layouts and mods there are replaced on every start. To customise one, clone it with `herdr-app do layout.clone` / `mod.clone`, then add a `!` exception for the clone to `.gitignore`. After an edit, check for a `<name>.error` file next to the edited file.
- The personal layout is `layouts/main-copy.json`, which is tracked. The plugin installers below cloned it from `main` and edit it on install and uninstall, so commit it after running any of them.
- Plugins (app mods) aren't tracked, because their folders hold binaries and machine-specific paths. The one exception is `mods/gitview/` (the main herdr-gitview mod, which carries the local patch below): its JS, `mod.json` and icons are tracked, while its `bin/`, `config.json` (absolute paths) and typings stay ignored, and its sibling `gitview-*` mods aren't tracked. On a new machine, open the app and reinstall them; each command also updates its plugin:
  - herdr-nvim: `curl -fsSL https://raw.githubusercontent.com/ChmaraX/herdr-nvim/main/install.sh | sh -s -- --app`. Its settings are in the tracked `.config/herdr-nvim/config.toml`. `tree = "nvim"` makes `cmd-e` open nvim alone, without the native file tree. Change it with `~/.config/herdr-app/mods/herdr-nvim/bin/herdr-nvim app-config tree native|nvim`.
  - herdr-gitview: `curl -fsSL https://raw.githubusercontent.com/ChmaraX/herdr-gitview/main/install.sh | sh -s -- --app`
  - herdr-chat: `curl -fsSL https://raw.githubusercontent.com/ChmaraX/herdr-chat/main/install.sh | sh -s -- --app --no-subagents`. Without `--no-subagents` it writes a block into `~/.claude/CLAUDE.md` and templates into `~/.config/herdr-core/templates/`. `⌘I` opens a Claude Code chat and `⌘⇧I` opens the agent picker. Those keys are set in the tracked `data/herdr-chat/keys.json` (`"global"` part), which the installer applies to `keys.json`. The tracked `data/herdr-chat/settings.json` is the chat's own config (the installer never writes it): its `claude.args` start every chat with `--model fable --permission-mode auto`. The thinking level comes from `~/.claude/settings.json`'s top-level `effortLevel` (set to `high` there; the chat host ignores `--effort` and `modelSettings`), which the CLI uses too.
  - herdr-auto-title: copy `mod/mods/auto-title` from a tagged release of kryptamine/herdr-auto-title into `mods/`, then press `cmd-alt-t` → Install. The popup installs a login service that updates itself.
  - Uninstall: the same command with `--uninstall`. For auto-title, run `~/Library/Application\ Support/herdr-auto-title/bin/herdr-auto-title desktop uninstall` and delete `mods/auto-title`.
  - The plugin keys are already in the tracked `keys.json`, and the installers only bind free keys.
- `herdr plugin` belongs to the terminal `herdr`, not the app. The app doesn't use it.
- Icons: `programs.json` swaps the one-color nvim, lazygit and shell icons for the colored SVGs in `my-icons/`. Tabs holding only a mod pane (the chat, gitview) have no program, so the tab bar shows no icon for them. `mods/tabs-icons/` is a clone of Herdr's `tabs` mod made with `mod.clone`, with a `MOD_ICONS` fallback added, and `main-copy.json` uses it instead of `tabs`. Clones never get Herdr's updates; to pick up a newer `tabs`, clone it again and re-add `MOD_ICONS`.
- `mods/prs/` is our own mod and is tracked. Without props it's the "Pull requests" list under Agents in the sidebar of `main-copy.json` (`list.js`): your open GitHub PRs grouped by repo, read with `gh api graphql` once a minute (so `gh auth login` must be done). The circle on each row is the head commit's combined CI state (green passed, red failed, spinner running, hollow none); clicking it opens the Jenkins build behind the status (the Jenkins URL GitHub reports, a failing one first). Clicking the row opens the PR as a tab named `#<number>` in the shown space: the same mod with props `{view: {repo, number}}` (`view.js`): the diff in a virtual list with review threads under their lines (`diff.js` parses `gh pr diff` and anchors `pulls/<n>/comments`), a Comments tab (description, reviews, comments, threads as markdown), a GitHub button, a Space button (a space named `<repo> #<n>` on the PR's branch: the clone in `~/vinted/<repo>` when it's already on that branch, else a git worktree of it at `~/.herdr/worktrees/<repo>/<branch>`; a fork's branch is fetched from the PR ref), the CI circle, and Close and Merge buttons that ask once before acting. Close runs `gh pr close`. Merge sends GitHub's `enqueuePullRequest` mutation when the base branch has a merge queue ("Queued" then, with a chip; `gh pr merge` would enable auto-merge instead, which those branches may refuse), else runs `gh pr merge --auto` (squash if the repo allows it, else merge, else rebase): a green PR merges at once, a blocked one gets auto-merge so GitHub merges it when the requirements are met; the confirm row says which. Next to Merge, `Comment "merge this please"` posts that comment with `gh pr comment` (also after a Yes), for the repos where a bot merges on it; the text is `MERGE_COMMENT` at the top of `view.js`. Approve (`gh pr review --approve`) asks nothing; it's off once you've approved, or on your own PR. A refusal from gh stays under the header until the next try. A comment box sits under the Comments tab (`↩` posts, `⇧↩` a new line): on the PR (`gh pr comment`), as a reply to a thread (its card's Reply button; `pulls/<n>/comments/<id>/replies`), or on a diff line: clicking a line in the Diff tab aims the box at it (the line is tinted, the box appears under the diff; the same line again or Esc takes it off) and posts a review comment on the head commit (`pulls/<n>/comments` with `commit_id`, `path`, `line`, `side`: LEFT for a removed line). A merged PR gets a `<base>: CI …` chip from its merge commit's status rollup, clickable like the circle, to follow the release. After any of them, shared `prs.refresh` makes the list re-read. Each sidebar row also has a link button that copies the PR's URL (`pbcopy`) and a folder button that opens the PR as a space (`openSpaceFor` in `gh.js`); a space already open for the PR, by name or folder, is shown instead. Under the repos are two foldable sections, folded at start, each with its count and a badge shown folded or not. "To review": open, non-draft PRs of the last 7 days (`REVIEW_DAYS`) that ask the `TEAM` at the top of `list.js` (`vinted/resilience`) for a review, by others (not by `SKIP_AUTHORS`, renovate's app), newest first, with `<repo>#<n> · <author>`, the PR's review state, "by you" once you've approved, a check button that approves at once (no question; a green circle-check after) and the badge `<n> not approved` (PRs whose review decision isn't APPROVED) or "all approved". "Merged": your PRs merged into `main` or `master` in the last 12 hours (`MERGED_HOURS`), whose circle is the merge commit's CI on that branch (the release pipeline), with `<n> in CI` and `<n> failed` badges. All three come from one GraphQL request with three `search`es and `viewer { login }`. Only the circles show in the narrow rail.
- `mods/spaces-pinned/` is a clone of Herdr's `spaces` sidebar made with `mod.clone`, and `main-copy.json` uses it in place of `spaces`; it's tracked. It adds pinnable spaces: right-click a space → Pin (or Unpin) puts it at the top of its machine's list, above a thin line, with a pin icon on the row that unpins it. The ids are in shared `spaces-pinned.ids` (so pins survive a restart; a gone space's pin is dropped once its machine's layout has been read), and the mod runs `space.move` to make the real order match, so `ctrl-1..9` follow it. A pinned repo keeps its worktrees under it; a pinned worktree stands on its own. `spaces-pinned.pin` toggles the shown space's pin (`herdr-app do spaces-pinned.pin`, or bind a key); the palette-plus entry "Pin or unpin this space" and the space-picker (pinned first, with a pin glyph) read the same shared list. The right-click menu is `mods/space-menu/`, a clone of Herdr's `menu` with the Pin item first (its command `pin` is handled in `choose`, like `worktree`); also tracked. Clones never get Herdr's updates: to take a newer `spaces` or `menu`, clone it again and re-apply the parts marked at the top of each `main.js`.
- `mods/repo-picker/` is our own mod and is tracked: cmd-n (`mod.open:repo-picker` in `keys.json`, instead of `space.new`) lists the folders in `~/vinted`; type to filter, Enter makes a space named after the repo with the repo as its folder, or goes to the space that already has it. The sidebar's + still runs plain `space.new`.

- `mods/palette-plus/` is a copy of Herdr's `frame/palette` (the app rewrites `frame/`, so it can't be extended in place) with our entries in `EXTRA`: "New Claude Code agent in this space" (a chat tab, like cmd-i), and the two pickers. cmd-shift-p opens it (`mod.open:palette-plus`, instead of `app.palette`). To take a newer palette, copy `frame/palette/main.js` over it and re-apply `EXTRA`, the `act` branch in `go` and `mod.json`'s overlay.
- `mods/tabs-icons/` has no + button and no Changes button in the tab bar: tabs come from space-tabs and the diff lives in the gitview tab. Re-add the two lines near the end of its `render` to get them back.
- `mods/git-actions/` is our own mod and is tracked: push and pull requests from the keyboard inside gitview, lazygit-style. It draws nothing (a root `floating` block in `main-copy.json` that only takes commands). `keys.json` binds them while a gitview pane has the keyboard (`mod:gitview` and `mod:gitview-diff` sections; gitview passes keys it doesn't use to the app): `P` → `git-actions.push` (`git push`, `-u origin <branch>` the first time; refuses when behind; toasts for progress and result) and `o` → `git-actions.pr` (lazygit's "open pull request"): a popup with the title and description (from the last commit), `⌘↩` creates it, pushing first when needed, `⌘D` makes it a draft, `⇥` moves to the description, `Esc` cancels; a branch that already has an open PR gets its `prs` tab instead. `c` → `git-actions.commit`: a popup for the commit message, `↩` commits (the staged changes, or everything when nothing is staged, as gitview's own box did; the header says which, decided when it opens), `⇧↩` a new line, `Esc` cancels; a failure stays under the box with the message. `i` → `git-actions.ignore` and `I` → `git-actions.exclude` add the file gitview shows (shared `gitview.views` for the focused tab) to the repo's `.gitignore` or `.git/info/exclude`, lazygit-style; a tracked file is first taken out of the index (`git rm --cached`) so the rule takes effect, and the toast says so. In the file list, space is gitview's own `gitview.button:stage:section:changes` (stages everything under Changes; the diff pane keeps space for paging). All five also run from `herdr-app do git-actions.push` / `.pr` / `.commit` / `.ignore` / `.exclude`, and the gitview one only while a gitview list is shown. Gitview's own footer and `?` card don't know these keys (its files are the plugin's), with one exception: `mods/gitview/modes.js` is patched so its `c` runs `git-actions.commit` and the commit box under its file list is gone, because the `mod:gitview` keys fire inside that box too, so typing a message there ran them (a space staged everything). Reinstalling herdr-gitview undoes the patch: run `mods/git-actions/patch-gitview.sh` again (it skips an already patched file), or `git checkout .config/herdr-app/mods/gitview` to go back to the tracked copy; `git status` shows the plugin's own changes after an update, so commit them if you keep them.
- `mods/status-bar/` is our own mod and is tracked: the bottom bar in place of Herdr's `workspace-status`, without the machine name and the agent count. It has the FortiClient VPN state (polled every 5 s: green with the profile name when connected, red "VPN off" when not) and the palette hint. "Connected" is the SSL network extension (`scutil --nc status VPN`) or FortiClient's IPsec processes (`iked`, `fct_tunnel_ctl`; the `vinted-vpn v2` profile is IPsec). The chip toggles: nothing starts a tunnel from the command line (the service ignores `scutil --nc start`, FortiClient's CLIs need root, `fabricagent://vpn` only opens its VPN page), so connecting presses the profile's Connect button in FortiClient's window through `vpn.applescript` (Electron: it turns on `AXManualAccessibility` first), and disconnecting uses `scutil --nc stop VPN` for SSL or the Disconnect button for IPsec. FortiClient is opened in the background (`open -g`) and hidden again after the press, so its window doesn't come up. Herdr needs Accessibility permission for that (System Settings → Privacy & Security); without it the chip says so in a toast. The profile is `VPN_PROFILE` at the top of `main.js`. `status-bar.vpn` (toggle), `status-bar.connect` and `status-bar.disconnect` are mod commands for a key or `herdr-app do`; each action writes a line to `data/status-bar.log` (untracked).
- `mods/blank/` draws nothing. It fills the sidebar's top block in `main-copy.json` (36 px, still the window-drag area under the traffic lights) in place of `workspace-chrome` (the Herdr title, search and collapse buttons); the sidebar footer block (Settings, Add machine) is `hidden`. Settings are still in the palette and the app menu.
- The look is `themes/misty-mountains.json`, set as `theme` on the root of `main-copy.json` and tracked: gruvbox material (medium) colours, so the terminal background is nvim's `#282828` and the padding around it is seamless. Panels are warm stone (`canvas` darkest, then `chrome` for the sidebar and bars, `background` for the cards), text is parchment (`foreground`, then `muted` and `dim`, all at 4.5:1 or better on the sidebar), the one accent is the blue-aqua `#7daea3` (focus ring, selected tab, links), and the agent states are amber working, red blocked, green done, grey idle. Dark only. The UI font (sidebar, tabs, chat; not the terminals) is `ui_font` on the same root: Iowan Old Style, which ships with macOS, so nothing to install. Changing a colour in the file applies live; the theme picker in Settings rewrites the root `theme`, so put it back after trying another one.
- Panes have no header: `main`'s `pane` in `main-copy.json` has no `header` (herdr-nvim's `herdr-nvim-header` used to be there); the border, focus outline and radius stay.
- `mods/space-tabs/` is our own mod and is tracked. Every space on this machine gets a claude chat, nvim (`nvim .`, which opens oil) with a shell pane below it at 25% height, and gitview, in that order, ahead of the tabs it already has. `pane.split` takes no size, so the mod writes pane weights into herdr-core's `herdr-app` document (`hc connect`, `doc.get`/`doc.set`). The tab list is `TABS` in its `main.js`. It runs from the `space-tabs` floating block in `main-copy.json`. Each space is set up once (ids in shared `space-tabs.seeded` and `space-tabs.nvim-shell-2`), so a tab closed later stays closed. Tabs open in their final order and the starter shell closes at once; gitview-tab focuses its file list when built, which shows its tab, so the claude tab is held until it has stayed shown for a second. The loop looks for new spaces every 200 ms. When creating a mod, Herdr adds a visible copy of it to the shown layout; remove that block from `main-copy.json` if the mod belongs in `floating` instead.
- `mods/kube/` is our own mod and is tracked: a k9s-like Kubernetes tab, a new one on every cmd-k (`kube.open`, taken by the `kube-commands` floating block in `main-copy.json`; also in palette-plus and `herdr-app do kube.open`; it starts as `k8s` and the view renames it `<context> - <namespace>`, by the focused tab, whenever they change; `tabs-icons` gives it the kubectl icon by mod name), or `tab.new` with `mod: "kube"` and props `{context, namespace, tab: "pods", allNs, resource}` or `{pod, action}`. It reads clusters with `kubectl --context <ctx>` (`kubectl.js`), never kubectl's current context; the terminal button in the header runs `kubectl config use-context` for the shells. Auth is kubelogin as in the shells (a cached token is used silently; when it must log in, kubectl waits for the browser, so calls have a long timeout, and after any error the 30 s auto-refresh stops until a manual refresh so a failed login doesn't reopen the browser). Header: a context dropdown (`c`; prod contexts, by the `oidc-kubelogin-prod` user, carry a red `prod` chip) and a namespace dropdown (`n`; the context's namespaces, the recent ones first with digits `1`–`9`, `0` is all namespaces; a name not in the list can be typed), kept in shared `kube.last` and `kube.recent`; `:` opens a k9s-style command line: a resource by name, short name, kind or alias (`dp`, `sec`, `jo`, `no`; the rest from `kubectl api-resources`, cached per context), `ctx <name>`, `ns <name>`, `wl`/`pp` for the two built-in views. Views: Workloads (`w`): Deployments, Argo Rollouts and StatefulSets (one `get` of the kinds with HPAs; a cluster without the Rollout CRD is retried without it) with a health word (`health` in `kubectl.js`), ready/desired, up-to-date, available, the HPA as `min–max · metric now/target` (red when at max) and age; Enter lists a workload's pods by its selector. Problem pods (`p`): pods that aren't Running, are Terminating, or have a container not ready (the API's `status.phase!=Succeeded` filter, then jq); with all namespaces only the cluster's Pending/Failed/Unknown pods (an API field selector), so never a cluster-wide pod dump; Enter expands conditions and container states. Any other resource is kubectl's `-o wide` table parsed by the header's column starts (`parseTable`); on the `namespaces` table Enter uses the namespace. Rows are selected with `j`/`k` or a click; the footer lists the keys that apply: `d` describe and `y` yaml (a read-only code view in the tab, Esc back), `l` logs (a log view in the tab: the last 500 lines with `--timestamps`, then every 2 s the lines since `--since-time`, one container or all with `--prefix`, `f` follows the end, `c` cycles containers, `t` timestamps, `o` the old `kubectl logs -f` terminal tab), `e` edit (`KUBE_EDITOR=nvim kubectl edit`, then the list is re-read and a toast says how it ended), `s` shell for pods, `⌃d` delete, `D` in Problem pods deletes every listed troubled pod (`--wait=false`, one `kubectl delete` per namespace), `R` restart (`kubectl rollout restart`, or `spec.restartAt` on a Rollout), `P`/`F`/`A`/`U` promote, promote fully, abort and retry a Rollout (through the `kubectl argo rollouts` plugin when installed, else the same patches it makes, with `--subresource=status`), `h` edits the workload's HPA. Changes ask in the footer first (`y`/`n`, with "on PROD" in the question). Programs (edit, shell, `o`) run in a terminal tab of the space started with `hc run --label herdr.space/herdr.tab` (`program` in `view.js`; hc runs through `exec` like kubectl, never the app's blocking helper), so the tab closes when nvim or kubectl ends; the edit waits on it with `hc wait`. A loading chip in the header shows what's being read.
- `mods/thanos/` is our own mod and is tracked: a Thanos (Prometheus API) tab, opened from the palette (cmd-shift-p, "New Thanos tab"; the command is `thanos.open`, taken by the `thanos-commands` floating block in `main-copy.json`, also `herdr-app do thanos.open`; no key is bound to it on purpose; it starts as `thanos` and the view renames it `thanos · <first query>`; `tabs-icons` gives it the chart icon by mod name), or `tab.new` with `mod: "thanos"` and props `{query}` or `{queries: [...]}` and `{range: "3h"}`. The Thanos URL is `url` in `data/thanos/config.json`, which isn't tracked (the repo is public; the mod writes a template when it's missing and the header says so). Queries go through the app's `fetch` (`thanos.js`; the VPN must be on; fetch gives up after 30 s, and its 8 MiB body limit is why metric names are fetched by prefix with `match[]` rather than as one list). Nothing blocks: every query is its own task, panels run in parallel, and a reply for a panel that has moved on is dropped (a generation counter). The tab is a column of panels over one time range (`R` picks it: a duration from the list or typed, or a pasted Grafana `from=…&to=…` pair or URL (epoch ms or `now-6h`), two times (`2026-11-16 14:00 to 2026-11-16 15:30`), or a Thanos `/graph` link; `parseRange` in `thanos.js`. A relative range ends now and auto-refreshes every 60 s (`a` toggles that); a fixed window doesn't. `C` copies the range for Grafana as `from=…&to=…`; the step aims at about one sample per two pixels). While a query runs, the tab in the tab bar spins: the view keeps shared `thanos.busy` as `{ <tab id>: running count }` and `tabs-icons` reads it. Each panel has a query box, `▶` run, a graph/table toggle (`t`: a range query drawn as lines, or an instant query as a table that draws the first 50 rows until `e`/"show all"), a Format button (`f`: the query spaced on one line as Prometheus's pretty-printer does it, `format` in `promql.js`; every run formats first), Duplicate (`d`: a copy under it with the same query and result, to alter) and Remove (the × at once, a running query's reply is dropped; the `x` key asks in the footer first). The query box's keys are handled on the box itself, not the root: with the suggestion list open the `Popup` layer takes ↑/↓ before they'd reach the root. `n` adds a panel, `j`/`k` and `1`–`9` focus one, `↵` edits it. Graphs are drawn by the mod (`chart.js`): one stroked `PathBuilder` path per series through the global `window.paint_path`, in percent coordinates, with grid, axes, a legend (click hides a series, ⌥-click keeps only it) and a crosshair with the values at that moment. The crosshair's time is shared by every panel, so hovering one chart marks the same moment on all of them; `o` adds an Overlay card at the top with every panel's series in one chart; `-`/`=` change the chart height (chart.js still takes a `norm` flag for drawing each series as a share of its own max, but nothing sets it). Pitfalls found while building it are noted at the top of `chart.js` (don't import `window` from "herdr"; no `dash_array`; the plot box needs `h_full()`). The query box colours PromQL (`promql.js`, a lexer: strings, numbers and durations, keywords, aggregators and functions, label names inside `{}`, metrics, operators): the Input's own text is drawn transparent and the tokens are laid over it as spans, each at `BOX_PAD + index × CHAR_W` (7.5 px, JetBrains Mono's 0.6 em at 12.5 px), not end to end, because per-span widths round and drift along the line; the spans stay off when the text is wider than the box, since the Input would scroll. ↑ ↓ ⇥ ↵ Esc don't reach `on_key_down` handlers while an Input has the keyboard (the control keeps them), so `keys.json`'s `mod:thanos` section binds them to `thanos.key:<name>`, which feeds the same `key()` handler; a press that arrives both ways counts once. The query box completes (Tab, ↑↓, ↵ runs or takes the picked one): aliases, recent queries (shared `thanos.recent`), metric names (by their first two letters, from Thanos), label names of the metric before `{`, and label values after `label="`; the list is a `Popup` under the box so it paints above the charts. Aliases are `data/thanos/aliases.json` (not tracked; seeded from the tracked `aliases.example.json`): `name → { expand, hint }`, `$1`, `$2`… are the words typed after the alias, so `r5 http_requests_total` → `sum(rate(http_requests_total[5m]))`. Typed `(`, `[`, `{` and `"` close themselves (caret between), a typed closer steps over one already there, and Backspace on an opener removes its empty pair. `keys.json`'s `mod:thanos` section binds ⌘S → `thanos.link` (a Thanos `/graph` URL with one `g<n>` per panel to the clipboard, through pbcopy), ⇧⌘S → `thanos.shot` (`herdr-app shot`, cropped with sips to the focused panel when the pointer has been over it, else the tab, else the window, then onto the clipboard as PNG through osascript) and ⌘↵ → `thanos.run`; `thanos.new`, `thanos.duplicate` and `thanos.refresh` exist too, all for `herdr-app do` as well. For shells and agents: `thanos.add:<expr>` adds a panel with that query to the shown Thanos tab and runs it (the commands block opens a tab with it when none is shown), `thanos.shot:<file>` saves the screenshot to a file instead of the clipboard, and `thanos.dump:<file>` writes the panels with a summary of each series (last, min, max, avg) as JSON; the file must be under `~/.config/herdr-app`, because mods can't write elsewhere. `bin/thanos` wraps all of it: `query` (instant, or `--range` for last/min/max/avg per series; `--json` for the API's data), `names`, `labels`, `values` for completion-style lookups, `show` (queries into the person's tab, `--new` for a new one), `tab` (what the shown tab has), `shot --out`, `link` and `url`; it reads the same `data/thanos/config.json`, and its `--help` tells an agent when to use which.

## zsh

- The repo `.zshrc` is the generic, public shell config, and `.stow-local-ignore` keeps it out of `~`. `~/.zshrc` on the work machine is a separate, untracked file with work aliases and credentials.
- For a change you want on every machine, edit the repo `.zshrc`, and apply it to `~/.zshrc` too if it should take effect here. Never copy anything from `~/.zshrc` into the repo without checking it for work-specific paths, hosts and passwords. The repo is public on GitHub.
